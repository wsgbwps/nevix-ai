# Server code rules

- Put every business Module under `internal/<module>/`; do not add business packages directly under `server/`
- Keep a simple Module in `internal/<module>/module.go`, and extract a Repository interface only when a second adapter is introduced
- Adopt the four layers only when the Module has the complexity described by [ADR-0003](../docs/adr/0003-complexity-driven-ddd-layering.md): entities, value objects, and Repository interfaces in `domain/`; use-case orchestration in `application/`; adapters and Repository implementations in `infrastructure/`; HTTP registration/handlers in `interface/`
- When distinct responsibility clusters emerge inside a simple Module, split them into responsibility-named sub-packages (identity: `command/` + `verification/` + `outbox/`) with `module.go` remaining the composition surface
- Keep `cmd/server/main.go` as the composition root: construct dependencies and call each Module's exported `Register(r chi.Router, bus event.Bus)` and `RunWorkers(ctx)`; never use `init()` with a blank import. The composition root and a Module's integration tests import only the Module package itself, never its sub-packages; package-local tests stay inside the package they test
- Place tests by boundary, not by resources: tests exercising a Module's public seams (`NewModule` wiring, `Register`/`RunWorkers`, GoTrue/PostgREST data plane, SMTP delivery, OpenAPI conformance) live in that Module's `integrationtest/` package; tests verifying one package's internal responsibility (SQL, query plans, transactions, catalog) stay in that package even when they use the real database, named `*_integration_test.go` (a resource label, not a build tag)
- Keep test support inside `_test.go` compilation units: shared infrastructure helpers (environment gating, database pools, Module/Worker lifecycle, key servers, mail clients, router mounting) live in their own named test-support files inside the owning test package (identity: `harness_test.go`, `mailpit_support_test.go`, `jwks_server_test.go`, `transport_support_test.go`), while scenario fixtures stay with the scenario tests that use them; do not create an importable test-support package or a cross-Module testkit until a second real Module consumer exists with the same protocol and lifecycle
- Keep the real-database opt-in contract uniform across packages: without `NEVIX_IDENTITY_INTEGRATION_REQUESTED` a missing environment skips; with the flag set (the dedicated harness entry) a missing environment fails; the dedicated run must finish with zero skips and representative sentinels passing
- Business Modules under `internal/` must not import each other; cross-Module communication goes through the shared `internal/event/` event bus, with all Domain Event types defined centrally in `internal/event/types.go`
- Put genuinely cross-Module infrastructure in shared sub-packages under `internal/` (e.g. `internal/event`); do not create a top-level `pkg/` directory (see [ADR-0005](../docs/adr/0005-no-pkg-directory.md)). Shared sub-packages are shared areas governed by the root approval rules
