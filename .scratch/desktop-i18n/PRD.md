# PRD: Desktop Multilingual Support

Status: ready-for-agent

## Problem Statement

Nevix 桌面端目前没有多语言基础设施，用户可见文案直接写在各自界面或桌面生命周期配置中。中文用户、英文用户以及系统语言不受支持的用户无法获得一致、可预测的界面语言体验，也无法在不登录、不联网的情况下主动切换语言。随着 Feature 增加，如果继续散落硬编码文案，翻译完整性、跨进程一致性和多人协作边界都会迅速失控。

## Solution

为 Desktop 引入简体中文和英文两种 Supported Language，并提供“跟随系统（默认）”“简体中文”“English”三种 Language Mode。主进程持有并在当前设备持久化 Language Mode，解析实际 Interface Language，再通过 `settings` IPC 与渲染进程保持一致；用户可在无需登录、无需联网的设置界面中立即切换语言。

所有 Desktop 拥有的 Localized Surface 都纳入文案本地化，包括渲染界面、窗口以及当前或未来的原生桌面交互、安装流程和系统权限说明。Interface Language 只改变文案，不改变时区、日期与数字格式、货币、计量单位或业务数据。各 Feature 分别拥有自身翻译资源，正式发布前由 CI 验证所有 Supported Language 的资源完整性。

## User Stories

1. 作为中文系统用户，我希望首次启动 Nevix 时自动看到简体中文，以便无需配置即可使用熟悉的语言。
2. 作为英文系统用户，我希望首次启动 Nevix 时自动看到英文，以便应用符合我的系统语言习惯。
3. 作为系统语言既不是中文也不是英文的用户，我希望 Nevix 回退到简体中文，以便界面始终使用一种正式支持的语言。
4. 作为用户，我希望设置页清楚显示当前 Language Mode，以便了解应用是在跟随系统还是固定使用某种语言。
5. 作为用户，我希望可以选择“跟随系统”，以便 Nevix 在后续启动时重新采用受支持的系统语言。
6. 作为用户，我希望可以固定选择简体中文，以便系统语言变化不会改变我的 Nevix 界面。
7. 作为用户，我希望可以固定选择英文，以便系统语言变化不会改变我的 Nevix 界面。
8. 作为用户，我希望语言切换立即更新当前运行中的界面文案，以便无需重启应用。
9. 作为用户，我希望语言切换后新打开的窗口、菜单、对话框、托盘交互和通知使用新语言，以便同一会话内没有语言不一致。
10. 作为用户，我希望语言选择在关闭并重新打开 Nevix 后仍然保留，以便不必重复设置。
11. 作为用户，我希望语言设置无需登录即可使用，以便登录前也能看懂界面。
12. 作为用户，我希望语言设置在离线状态下仍然可用，以便它不依赖网络或账号服务。
13. 作为在多台设备上使用 Nevix 的用户，我希望每台设备可以独立选择语言，以便设备偏好不会互相覆盖。
14. 作为处于“跟随系统”模式的用户，我希望 Nevix 每次启动时重新读取系统语言，以便系统语言变化能在下次启动后生效。
15. 作为应用运行期间修改系统语言的用户，我希望 Nevix 保持当前界面稳定，直到下次启动，以免界面在没有主动操作时突然变化。
16. 作为从固定语言切回“跟随系统”的用户，我希望当前会话立即采用本次启动时解析出的系统语言，以便切换结果立刻可见。
17. 作为用户，我希望品牌名 `Nevix AI` 在中文和英文界面中保持一致，以便品牌识别不受翻译影响。
18. 作为用户，我希望自己的输入、生成内容和业务数据保持原样，以便切换界面语言不会修改内容。
19. 作为用户，我希望服务端日志、第三方原文和其他非 Desktop 自有内容保持原样，以免应用错误地改写外部信息。
20. 作为用户，我希望切换语言只改变文案，不改变时区、日期与数字格式、货币或计量单位，以便本期行为简单且可预测。
21. 作为用户，我希望正式版语言选择器只展示翻译完整的语言，以免误入半中文半外文的界面。
22. 作为用户，我希望正式支持语言意外缺少文案时看到简体中文兜底，而不是空白或内部翻译 key，以便界面仍然可理解。
23. 作为开发者，我希望开发环境对缺失翻译给出显眼错误，以便在发布前发现问题。
24. 作为 Feature 开发者，我希望翻译资源与所属 Feature 一起维护，以便功能和文案在同一修改范围内演进。
25. 作为 Feature 开发者，我希望通过 Feature 的公共边界提供翻译资源，以便不破坏 Feature 之间的隔离规则。
26. 作为多人协作团队成员，我希望避免所有 Feature 共同修改一个巨型语言文件，以便减少合并冲突和共享热点。
27. 作为维护者，我希望 CI 只对 Supported Language 执行完整性门槛，以便其他语言可以渐进开发而不影响主干。
28. 作为维护者，我希望未完成语言不会因为资源文件存在就自动出现在正式版中，以便“有翻译资源”和“正式支持”保持不同含义。
29. 作为维护者，我希望主进程和渲染进程使用同一个权威 Language Mode，以便窗口、原生交互和 React 界面不会各自保存冲突设置。
30. 作为发布维护者，我希望安装流程和系统权限说明提供简体中文及英文文案，以便操作系统能在对应生命周期展示合适语言。
31. 作为发布维护者，我希望构建在任一 Supported Language 缺少必需文案时失败，以便不完整翻译不会进入正式版本。
32. 作为未来增加第三种语言的开发者，我希望可以先提交未完成资源而不向正式用户开放，以便翻译工作能够渐进进行。

## Implementation Decisions

- Desktop 当前没有 i18n、Language Mode 持久化或设置 UI 基础设施，本功能需要同时建立本地化运行时、设置垂直切片和资源完整性检查。
- 首期 Supported Language 只有简体中文 `zh-CN` 和英文 `en`。
- Language Mode 是设备本地设置，固定为三个值：跟随系统、简体中文和英文；默认值是跟随系统。
- 跟随系统模式在每次应用启动时读取最高优先级的系统偏好语言。中文语言族解析为 `zh-CN`，英文语言族解析为 `en`，其他语言解析为 `zh-CN`。
- Electron 运行期间不监听操作系统语言变化。当前启动解析出的系统语言保持稳定，下一次启动时重新解析。
- 缺失、损坏或无法识别的持久化 Language Mode 按“跟随系统”处理，不将无效值传播给渲染进程。
- 主进程是 Language Mode 的唯一权威来源，并将其保存在 Electron 的应用用户数据目录中；不得以渲染进程 `localStorage` 作为权威存储。
- `settings` IPC Domain 负责读取和更新 Language Mode。它遵循现有按 Domain 分散 IPC 类型与 handler 的约定，并复用通用 preload 桥，不添加 per-domain preload 代码。
- `settings` Feature 提供语言选择界面，并且在未登录、离线状态下可访问。首版不在顶部栏、托盘或原生菜单重复增加快捷入口。
- Language Mode 更新成功后，主进程立即更新自身 Interface Language，并通知当前渲染进程更新；当前页面不得为应用语言切换而重载或重启。
- 渲染进程在应用 Provider 层初始化本地化能力。主进程和渲染进程各自持有独立的 i18n 实例，不尝试跨 Electron 进程共享内存实例。
- 使用框架无关的 `i18next` 作为本地化核心，渲染进程使用 `react-i18next` 的 Provider 与 hooks。
- 只启用文案翻译能力。本期不引入日期、数字、货币、单位、时区或业务数据的区域化转换。
- 每个 Feature 拥有独立 namespace 和简体中文、英文资源，并通过该 Feature 的唯一公共出口暴露需要注册的资源；Feature 不直接导入其他 Feature 的内部翻译文件。
- 应用壳、设置 Feature、主进程和打包生命周期分别拥有自身 Localized Surface 的翻译资源。共享本地化层只负责语言解析、资源注册、翻译和变化协调，不拥有各业务 Feature 的文案。
- 品牌名、用户内容、服务端日志和第三方原文不得进入翻译资源。带有品牌名的复合文案只翻译 Desktop 自有部分。
- 安装器和系统权限说明提供简体中文与英文的打包时本地化资源，由操作系统生命周期选择；它们不承诺响应应用运行期间的 Language Mode 切换。
- 建立唯一的 Supported Language 注册表。只有在注册表中声明且通过完整性检查的语言，才出现在正式版语言选择器中。
- CI 针对每个 namespace 的必需消息契约验证所有 Supported Language：资源必须存在、必需 key 不得缺失、值不得为空。检查对象不是仓库中发现的所有语言资源，未注册的候选语言允许不完整。
- 简体中文是运行时 fallback language。生产环境发生意外缺词时显示简体中文；开发和测试环境必须报告可定位的缺失翻译错误。
- TypeScript 翻译类型从正式资源契约推导，静态字面量 key 应获得类型检查；动态 key 不能作为绕过完整性检查的常规手段。
- 本功能不新增 Supabase、Server、数据库、账号同步、网络 API 或云端 schema 变更。
- 本功能涉及应用启动层、共享本地化能力和依赖配置，实施时必须按项目规则安排额外 review，并保持每个 Feature 与 IPC Domain 的边界清晰。

## Testing Decisions

- 好测试只断言用户可观察行为和发布契约，不直接断言 React state、i18next 内部字段、IPC handler 实现或持久化文件内部结构。
- Desktop 当前没有测试框架或测试先例，只有 lint、TypeScript 检查和 Electron Vite 构建 seam。本功能新增一套 `@playwright/test` 测试框架，不再同时引入第二套单元测试框架。
- 最高层主 seam 是一组 Electron 应用集成测试：构建后启动真实应用，使用隔离的临时用户数据目录，通过设置 UI 操作 Language Mode，并通过可见文案和窗口行为断言结果。
- 集成测试以受控的启动时系统偏好语言分别覆盖中文、英文和不受支持语言，验证初始 Interface Language 依次为简体中文、英文和简体中文回退。
- 集成测试从设置 UI 切换语言，验证当前已挂载的界面文案立即变化，应用和页面不因切换而重启或重载。
- 集成测试使用同一个隔离用户数据目录关闭并重启应用，验证固定 Language Mode 覆盖系统语言并正确持久化。
- 集成测试再切回“跟随系统”并重启，验证应用重新按照启动时系统语言解析 Interface Language。
- 集成测试至少观察一个渲染界面文案和一个主进程拥有的 Localized Surface，例如窗口标题，以证明跨进程语言状态一致。
- 集成测试在无登录态和无网络依赖的环境中访问设置并切换语言，验证该能力不依赖账号或服务端。
- 第二个 seam 是同一测试 runner 执行的资源契约测试。它从 Supported Language 注册表出发，而不是扫描所有候选语言，逐个验证每个正式语言满足各 namespace 的必需消息契约且值非空。
- 资源契约测试验证未注册的候选语言不会进入正式语言列表，并允许候选资源在开发期间不完整。
- 运行时 fallback 测试通过测试资源制造一个缺失文案，验证生产配置返回简体中文、开发配置报告缺失 key；不得破坏正式资源来构造该场景。
- 所有既有质量检查继续通过，包括 Desktop lint、node/web TypeScript 检查和生产构建。
- 预期新增 Desktop `test` 命令；标准验证顺序是先构建 Desktop，再运行 Desktop 测试。根级 Turbo 是否聚合 `test` 不属于本功能的必要条件。

## Out of Scope

- 简体中文和英文之外的正式语言支持。
- 账号级或跨设备 Language Mode 同步。
- Supabase、Server、数据库、网络 API 或云端配置。
- 运行期间监听操作系统语言变化。
- 日期、时间、数字、相对时间、复数格式、货币、时区和计量单位的区域化。
- 用户输入、生成内容、业务数据、服务端日志或第三方原文的翻译。
- 品牌名 `Nevix AI` 的翻译。
- 机器翻译、翻译管理平台、外部译员工作流或自动文案生成。
- 右到左语言布局和 RTL 基础设施。
- 面向普通用户开放未完成的候选语言。
- 为语言切换新增顶部栏、托盘或原生菜单快捷入口。
- 为本功能重新设计完整设置中心或账号体系。
- 让安装器或操作系统权限提示响应应用运行期间的 Language Mode 变化。

## Further Notes

- 本规格使用 Desktop 领域词汇表中的 Localized Surface、Language Mode、Interface Language 和 Supported Language，不以含糊的 “locale” 同时指代用户选择和最终显示结果。
- ADR“翻译资源由各 Feature 分别拥有”约束资源归属，禁止回退为集中式巨型语言文件。
- ADR“Language Mode 由主进程持有”约束跨进程状态边界，禁止将渲染进程存储变成第二权威来源。
- 当前 Desktop 是 Electron、React 和 TypeScript 的轻量脚手架；设置、本地化和测试基础设施均需由本功能首次建立。
- 测试 seam 已选择为 Electron 应用级行为与 Supported Language 资源契约，避免为主进程、IPC、renderer 和存储分别创造低层测试 seam。
