# 06 — Split the unreadable Session outcome from secure-storage unavailability

**What to build:** `readPersistedSession` in `apps/desktop/src/main/authentication/session-store.ts` returns `unreadable` both when the envelope is genuinely corrupt and when `canPersistSecurely()` is temporarily false (e.g. a locked Linux keyring or a briefly unavailable Keychain). The renderer's restore flow deletes the Session file on `unreadable`, so a transient secure-storage outage permanently destroys recoverable ciphertext and forces a re-login.

**Blocked by:** None, but requires an approved written plan before implementation — this adds a new outcome to `PersistedSessionRead` in `apps/desktop/src/shared/ipc/authentication/types.ts`, which is a public IPC contract change.

**Status:** resolved

## Proposed direction

- Add a distinct outcome (e.g. `locked` or `storage-unavailable`) for "the ciphertext may be fine, but decryption is not possible right now".
- The renderer keeps the file on that outcome and shows the retryable restore-failure boundary instead of clearing local credentials.
- `unreadable` remains terminal: malformed envelope, wrong version, or a decrypt that fails while the backend reports itself available.

## Acceptance sketch

- Corrupt-envelope E2E cases keep their current terminal behaviour (file deleted, session-expired notice).
- A launch with `NEVIX_TEST_UNAVAILABLE_SECURE_STORAGE=1` and a valid on-disk envelope no longer deletes the file, and a subsequent launch without the flag restores the Session.

## Comments

- Raised by the PR #5 security review (medium severity): `unreadable` conflates corruption with transient unavailability, making a destructive clear reachable from a recoverable state.
- Resolved on branch `fix/session-read-storage-unavailable`, merged to `main` as `0aaaa64` (rollback: `git revert -m 1 0aaaa64`). Implemented per the approved plan: `PersistedSessionRead` gains `storage-unavailable`; `readPersistedSession` validates the envelope structurally before `canPersistSecurely()`, so a corrupt envelope stays terminal `unreadable` even during an outage; `restore()` routes `storage-unavailable` to the retryable `restore-failure` boundary with no file deletion, notice, or Supabase work. ## Agent Brief

**Category:** bug
**Summary:** Split a recoverable "secure storage unavailable" outcome out of the terminal `unreadable` outcome so a transient outage never destroys a valid session envelope

**Verification (confirmed during triage):**
The claim was verified against the code, not just the report. `readPersistedSession` in the main-process authentication session store returns `unreadable` on a single guard that ORs two unrelated conditions: a malformed/unparseable envelope (terminal) and `canPersistSecurely()` returning false (recoverable — e.g. locked Linux keyring, briefly unavailable Keychain). The renderer's `restore()` flow in the authentication feature model calls `clearPersistedSession()` whenever the read outcome is `unreadable`, then shows the `session-expired` notice. So a transient secure-storage outage at launch permanently deletes recoverable ciphertext and forces a re-login. A retryable `restore-failure` boundary already exists in the same restore flow (used for non-terminal refresh errors) and can be reused; the `NEVIX_TEST_UNAVAILABLE_SECURE_STORAGE=1` test hook already exists in the session store.

**Gate — written plan and PR required first:**
This change touches a public IPC contract (`PersistedSessionRead` in the shared IPC authentication types) and the authentication domain, which `AGENTS.md` classifies as high-risk. Before implementation, the agent must write a short plan under `.scratch/` and land the change through a branch and PR — not direct commits to `main`.

**Current behavior:**
- `PersistedSessionRead` has three outcomes: `session`, `empty`, `unreadable`.
- The session store returns `unreadable` both when the envelope is genuinely corrupt (bad JSON, wrong version, invalid base64, failed decrypt while the backend is available, malformed session shape, oversized envelope) and when secure storage is merely unavailable at read time.
- On `unreadable`, the renderer deletes the persisted session file and lands on `unauthenticated` with a `session-expired` notice.

**Desired behavior:**
- A new distinct read outcome (name to be settled in the written plan — e.g. `storage-unavailable` or `locked`) means "the on-disk ciphertext may be intact, but decryption is not possible right now". It is returned when `canPersistSecurely()` is false at read time, before any decrypt attempt.
- On that outcome the renderer must NOT delete the session file; it shows the existing retryable restore-failure boundary so the user can retry once the backend recovers.
- `unreadable` remains terminal and keeps its exact current semantics for: malformed envelope, wrong envelope version, invalid ciphertext encoding, oversized envelope, session-shape validation failure, and a decrypt that fails while the backend reports itself available. Its renderer handling (delete file, `session-expired` notice) is unchanged.
- File-read I/O errors other than ENOENT stay `unreadable` (unchanged).

**Key interfaces:**
- `PersistedSessionRead` union in the shared IPC authentication types — gains one new outcome member; this is the public IPC contract change that triggers the plan+PR gate.
- `readPersistedSession()` — the `canPersistSecurely()` check must be evaluated separately from ciphertext validity and mapped to the new outcome; ordering matters so that a corrupt envelope still reports `unreadable` even when storage is also unavailable is a decision the plan should state explicitly.
- The renderer restore flow — the "delete on unusable" step must key off `unreadable` only; the new outcome routes to the existing `restore-failure` (retryable) state without touching persisted data.

**Acceptance criteria:**
- [ ] A written plan exists under `.scratch/` and the change lands via a branch + PR.
- [ ] All existing corrupt-envelope E2E cases keep their current terminal behaviour: file deleted, `session-expired` notice shown.
- [ ] Launching with `NEVIX_TEST_UNAVAILABLE_SECURE_STORAGE=1` and a valid on-disk envelope shows the retryable restore-failure boundary and leaves the envelope file on disk.
- [ ] A subsequent launch without the flag restores the Session from that untouched envelope.
- [ ] A decrypt failure while the backend reports itself available still returns `unreadable` (terminal).
- [ ] Type-level exhaustiveness: every consumer of `PersistedSessionRead` handles the new outcome (compile passes with no ignored cases).

**Out of scope:**
- Changing write-path behaviour (`replacePersistedSession` / `PersistedSessionWrite` and its `unavailable` outcome).
- Adding automatic retry/polling for secure-storage recovery — a manual retry via the existing boundary is sufficient.
- Changing the `canPersistSecurely()` policy itself (e.g. the Linux `basic_text` rejection).
- Envelope format or version changes.
