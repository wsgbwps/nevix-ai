# 08 — Session store hardening follow-ups

**What to build:** Two low-severity hardening items in the authentication session persistence path, kept together because both are small, behaviour-preserving, and touch only the authentication Domain.

**Blocked by:** None.

**Category:** enhancement
**Status:** resolved

## Items

1. **Do not delete the previous good envelope on a failed replace.** `replacePersistedSession` in `apps/desktop/src/main/authentication/session-store.ts` removes both the pending file and the existing Session file when a write fails. The `rename` is atomic, so a failed pending write never corrupts the existing envelope; deleting it forces an unnecessary re-login on the next launch. Keep the fail-closed guarantee (never plaintext) while preserving the last successfully written ciphertext.
2. **Bound the transient key map in the renderer storage adapter.** `transientValues` in `apps/desktop/src/renderer/src/features/authentication/session/persisted-session.ts` grows without limit for non-Session keys written by supabase-js (PKCE verifiers and similar). Cap or expire entries so a long-lived renderer cannot accumulate them indefinitely.

## Acceptance sketch

- A simulated write failure (e.g. read-only pending path) leaves the prior envelope intact and the next launch restores the Session.
- The adapter never stores more than a small fixed number of transient keys.

## Agent Brief

**Category:** enhancement
**Summary:** Two behaviour-preserving hardening changes in the authentication session persistence path: preserve the last good envelope on a failed replace, and bound the renderer's transient key map.

**Current behavior:**

1. When `replacePersistedSession` fails (encryption error, mkdir/write/rename failure), its error path removes both the pending file *and* the existing Session envelope file. Because the new envelope is written to a `.pending` path and promoted with an atomic `rename`, a failure can never corrupt the existing envelope — yet it is deleted anyway, forcing an unnecessary re-login on the next launch.
2. The renderer storage adapter (`persistedSessionStorage`, a `SupportedStorage` implementation) routes every non-Session key written by supabase-js (PKCE verifiers and similar) into an in-memory `Map` with no size bound. A long-lived renderer can accumulate entries indefinitely.

**Desired behavior:**

1. A failed replace still cleans up the pending file and still returns `{ outcome: 'unavailable' }` (fail-closed: never plaintext, never a partially written envelope promoted), but the previously persisted ciphertext envelope survives, so the next launch restores the prior Session.
2. The transient key map holds at most a small fixed number of entries (eviction or expiry — implementer's choice); Session-slot behaviour (`AUTHENTICATION_STORAGE_KEY`) is unchanged.

**Key interfaces:**

- `replacePersistedSession(session: string): Promise<PersistedSessionWrite>` — outcome contract unchanged; only the failure-path filesystem side effects change
